# Codrops RainEffect 水滴轮廓与运动机制拆解

更新时间：2026-08-15  
范围：只研究 Codrops 官方 `RainEffect` Demo 与仓库源码，并映射到当前 `src/style/post.ts` 的低分辨率 `CanvasTexture + FullScreenQuad` 实现。本文件不修改运行时代码。

## 先给结论

参考站的真实感不是来自“把一个椭圆拉长”。它由四套机制共同形成：

1. 一张专门绘制的柔边水滴轮廓图负责主水滴，不是 Canvas 的标准椭圆；
2. 主水滴移动时剥离出多个独立小滴，小滴留在后方，视觉上才形成上细、下方水头较大的复合轮廓；
3. 水滴获得随机重力脉冲后下滑，同时持续减速到零，因此会出现“落一段、停一下、再落”的粘滑运动；
4. 大滴吸收小滴后面积增大并获得额外动量，所以会突然加速滑走，而不是所有水滴匀速下降。

当前实现最需要改的不是颜色，而是：删除连续拖尾线、把单一椭圆改成不对称水头、让速度能够真正衰减到零，并让全屏微小水滴参与聚合或被大滴吸收。

## 1. 参考站的水滴轮廓是怎样形成的

### 1.1 它不是程序画出的固定椭圆

`renderDropsGfx()` 先把 `drop-color.png` 与 `drop-alpha.png` 合成为 255 个不同“厚度”的缓存水滴 sprite。`drawDrop()` 再按水滴半径、横向扩散和纵向扩散选择一个 sprite，并把它绘制成宽度 `2r`、高度 `3r` 的基础比例；也就是基础 `scaleX = 1`、`scaleY = 1.5`。

来源：[`raindrops.js` 第 104-165 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L104-L165)。

`drop-alpha.png` 是一张 128x128 的柔边水滴遮罩。它不是数学圆或椭圆；`drop-color.png` 的 R/G 通道描述折射方向，B 通道被用作厚度。`water.frag` 将 G、R 分别解释为折射向量的 x、y，将 B 解释为厚度，再用厚度调节折射距离和高光。

来源：[`water.frag` 第 86-113 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/shaders/water.frag#L86-L113)。

### 1.2 “下方水头 + 上方细尾”主要是多个水滴叠出来的

参考实现没有给主滴焊接一根长尾。主滴移动一定距离后，会在它身后生成一个半径只有主滴 20%-50% 的独立子滴。主滴继续向下，子滴留在原处；连续几次生成后，就形成不规则的小滴链。快速水滴生成子滴更频繁，但每次生成还会让主滴半径缩小约 3%，因此尾部不会无限变成长水柱。

来源：[`raindrops.js` 第 279-299 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L279-L299)。

子滴通过 `parent` 记录父滴，碰撞阶段明确排除父子立刻重新合并。因此参考站能保留离散尾随水珠，而不是刚生成就被主滴吃回去。

来源：[`raindrops.js` 第 319-349 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L319-L349)。

### 1.3 对当前项目的轮廓改写建议

不要复制 Codrops 的 PNG。当前凝露纹理只需要存高度和湿痕，可以用独立设计的程序化轮廓完成同样的视觉语义：

- 主水头：中心放在水滴逻辑位置下方约 `0.15r-0.25r`，横向半径约 `0.72r-0.86r`，纵向半径约 `0.82r-1.0r`；
- 上方颈部：在水头上方叠一个较窄、透明度较低的水滴瓣，宽度约主水头的 30%-48%；
- 速度只拉长颈部和上缘，不要把整个水头缩放成胶囊；
- 尾随效果只画离散小滴，不在相邻小滴之间画连续线段；
- 各滴的颈部偏左或偏右少量随机值，避免所有水滴共享同一轮廓。

当前 [`post.ts`](../../src/style/post.ts) 的 `drawMask()` 使用中心对称的径向渐变椭圆，所有主滴只改变纵向拉伸值，所以容易出现“同一个固定椭圆反复复制”的感觉。尤其是连接 trail 点的绿色连续 stroke，不存在于 Codrops 的视觉构成中，应移除。

## 2. 为什么有的水滴快落，有的停停走走

### 2.1 新水滴大小与初速度本来就不同

参考实现将大滴半径随机分布向小值偏置：半径随机数先做三次方插值。初始纵向动量由 `1 + (r - minR) * 0.1 + random(2)` 得到，所以初生的大滴天然更快。默认参数为 `minR=10`、`maxR=40`；不同 Demo 会覆盖为 `20-60` 等范围。

来源：[`raindrops.js` 第 22-42 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L22-L42)、[`raindrops.js` 第 192-215 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L192-L215)。

### 2.2 重力不是每帧固定加速度，而是随机脉冲

每一帧是否获得重力动量由水滴半径决定。越大的水滴，触发“creeping down”的概率越高；触发后才增加一段随机动量。小滴可能长时间不动，大滴更容易继续滑动。

来源：[`raindrops.js` 第 264-270 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L264-L270)。

### 2.3 动量会持续衰减到零

水滴更新位置后，参考实现每帧主动降低 `momentum`，并把负值钳制为 0。动量为 0 时，水滴不会移动；直到之后随机重力脉冲再次触发，它才继续滑落。这就是“落一下、停一下、再落”的核心，而不是预先写死几秒暂停动画。

来源：[`raindrops.js` 第 301-313 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L301-L313)、[`raindrops.js` 第 354-357 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L354-L357)。

当前 `post.ts` 的水滴在初始 `wait` 结束后只会继续获得非负加速度，`vy` 不会自然回到 0，因此严格说只有“先等再持续滑”，没有参考站的粘滑节奏。

### 2.4 可落到当前归一化坐标的参数区间

建议保留当前最多约 18 个活动大滴，但把运动改成动量脉冲模型：

| 参数 | 建议区间 | 作用 |
|---|---:|---|
| 活动大滴半径 | `0.014-0.042` 屏幕高度 | 小滴更容易停住，大滴更容易滑动 |
| 初始动量 | `0-0.010` UV/s | 大多数初生水滴先附着 |
| 重力脉冲检查 | 每个 60 Hz 逻辑步一次 | 不用固定动画时间表 |
| 脉冲概率 | 随半径从约 `0%-8%/步` 增长 | 形成尺寸相关的停走差异 |
| 单次动量增加 | `0.012-0.040` UV/s | 有短滑，也有快速滑落 |
| 动量衰减 | 每秒约 `0.035-0.075` UV/s | 必须允许速度回到 0 |
| 横向动量衰减 | 每秒保留约 `15%-35%` | 合并后短暂偏转，随后回正 |

这组数值是对当前归一化坐标和浴室技能节奏的改写起点，不是 Codrops 源码的像素单位照搬。关键验收条件是：同屏同时存在静止、短滑、间歇滑和快速离屏四种状态。

## 3. 小滴如何汇聚变大并突然快速落下

参考实现先按位置排序，只检查当前滴后面的有限邻居。较大的水滴吸收较小水滴，并排除父子滴。合并半径按面积计算：`sqrt(r1^2 + 0.8 * r2^2)`，即只保留被吸收滴约 80% 的面积，防止尺寸膨胀过快。

合并后还会：

- 给主滴增加一个由两滴横向距离产生的短暂横向动量；
- 清除原有拉伸状态；
- 将被吸收滴标记为死亡；
- 取两者较大的纵向动量，并额外增加与新半径相关的碰撞动量。

因此小滴汇聚后不仅变大，而且更容易马上快速下滑。来源：[`raindrops.js` 第 315-351 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L315-L351)。

当前项目已经有活动大滴之间的面积加权合并，但全屏 `microDrops` 是静态三元组，不会被吸收。因此看不到“一个小滴慢慢长大后突然滑走”。建议让少量微滴成为可吸收对象：

- 全屏静态微滴可维持约 160-240 个，只负责玻璃颗粒感；
- 其中约 20%-30% 标记为可生长凝结核；
- 大滴经过附近时吸收凝结核面积，并从微滴列表移除；
- 相邻凝结核也可以低频合并，半径超过约 `0.012-0.016` 后晋升为活动滴；
- 合并后立即提高一次动量，并在 `0.25-0.7s` 内降低附着阻力，形成快速滑落窗口。

这样不需要模拟几百个完整刚体，也能产生用户在参考站看到的“聚大以后突然落下”。

## 4. 尾随小滴与擦除路径

### 4.1 参考站没有一条可见的连续拖尾线

它使用两种不同信息：

1. 独立子滴：主滴滑动时从后方剥离，构成可见的小滴链；
2. 擦除路径：背景微滴存在单独的持久 Canvas 上，移动大滴使用 `destination-out` 的椭圆刷头擦掉经过区域的微滴。

来源：[`raindrops.js` 第 132-177 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L132-L177)、[`raindrops.js` 第 228-250 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L228-L250)、[`raindrops.js` 第 360-363 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L360-L363)。

擦除路径本身不是发亮的水柱。它只是让主滴经过的位置暂时少一些细小水珠，所以观众能感到一条湿痕，但不会看到规则直线。

### 4.2 拖尾生成频率与速度相关

参考实现把 `momentum * timeScale * trailRate` 累加到距离计数器。速度越快，越早越过下一次生成阈值；生成后阈值又减去与速度成正比的项，因此高速水滴会留下更密集的小滴链，慢滴则可能完全没有尾随小滴。

来源：[`raindrops.js` 第 279-297 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L279-L297)。

对当前实现的直接建议：

- 删除 trail 点之间的 `stroke()`；
- 仅当本次滑动累计距离超过主滴半径的约 `0.8-1.8` 倍时生成一个子滴；
- 子滴半径取主滴的 `0.18-0.36`，位置在主滴后方并带少量横向随机；
- 高速时缩短下一次距离阈值，但限制同一滴每秒最多约 4-7 个子滴；
- 湿痕单独写入 G 通道，用柔软、不连续的刷点表达，不要把各点连成一条直线；
- 湿痕应缓慢重新起雾，而不是一直保留。

## 5. 细小水滴如何参与“模糊视线”

参考实现的细小水滴不是只分布在顶部和两侧。`updateDroplets()` 在整张画布上持续随机生成微滴，半径使用平方插值，整体偏向更小的尺寸。它们被绘制到持久 Canvas，主水滴经过时才局部擦除。

来源：[`raindrops.js` 第 228-249 行](https://github.com/codrops/RainEffect/blob/5270be663903883ae585858216b656120d8d4cd5/src/raindrops.js#L228-L249)。

对浴室技能来说，细滴不应该把场景“擦清楚”。当前 shader 里微滴和主滴最终都可能混入清晰的 `tScene`，这会让白天箭头仍然很清楚。更合适的合成语义是：

- 无水滴区域：乳白、非均匀的磨砂扩散；
- 细小水滴区域：采样已经模糊的场景，再施加短距离、方向各异的折射；
- 主水滴区域：可以稍清楚，但仍以模糊场景为主，只混入少量清晰场景；
- 湿痕区域：降低雾层，而不是完全恢复原始清晰画面。

建议把主滴中的清晰场景占比限制在约 10%-22%，其余从模糊场景采样。微滴应改变局部折射和亮度，而不是直接提高可读性。这样白天箭头轮廓仍能辨认，但精确方向和边缘会被大量不均匀小滴持续打散。

## 6. 对当前 `post.ts` 的最小改造顺序

1. 先删除 trail 连线，只保留离散尾随小滴和低强度湿痕刷点；
2. 用“下方水头 + 上方窄颈”的程序化高度遮罩替换单一对称椭圆；
3. 将持续正加速度改为“随机动量脉冲 + 每帧阻力衰减到零”；
4. 让部分微滴可以被吸收并晋升为活动滴，合并后给予速度爆发；
5. 增加全屏微滴密度和尺寸层次，中下部也要存在；
6. 最后调整 shader：微滴折射模糊场景，主滴只少量恢复清晰场景，再略微增加磨砂底层。

这个顺序能先解决用户最明显看到的假水滴运动，再处理白天过清晰的问题，避免只继续增加全屏 Gaussian blur。

## 许可边界

Codrops 仓库 README 明确允许个人或商业项目集成或基于它继续构建，但禁止将原项目“as-is”重新发布、再分发或销售；`package.json` 也没有声明 MIT，而是指向 Codrops 自己的许可页。

因此当前项目最稳妥的方式是：

- 研究并独立改写运动机制；
- 自己程序化生成水滴高度与折射信息；
- 不直接复制 `drop-alpha.png`、`drop-color.png`、`drop-shine.png`；
- 不整段照搬 `raindrops.js`；
- 在第三方说明中保留 Codrops/Lucas Bebber 作为视觉与算法参考来源。
